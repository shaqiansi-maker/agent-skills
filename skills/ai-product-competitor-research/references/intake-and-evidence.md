# 输入与证据指南

## 首次使用的最小输入

用户只需提供四类信息，能从项目中读取到的无需重复询问：

```text
当前项目：一句话说明产品、用户和主要价值。
当前阶段：想法 / 原型 / MVP / 迭代 / 增长 / 平台扩展。
竞品：一个或多个名称、链接、截图或文档。
要支持的决策：例如定位、MVP、定价、Agent、支付、架构或增长。
```

若信息不足，优先读取可访问项目。只有缺失信息会改变结论时才追问。不要要求用户先填写长问卷。

## 项目上下文卡

```markdown
### 项目上下文卡
| 项目事实 | 当前判断 | 状态 | 来源 |
| --- | --- | --- | --- |
| 产品定位 |  | confirmed / user_stated / inferred / unknown |  |
| 核心用户 |  |  |  |
| 核心任务与购买理由 |  |  |  |
| 当前阶段与停止线 |  |  |  |
| 已构建能力 |  |  |  |
| 已承诺但未构建 |  |  |  |
| 商业模式 |  |  |  |
| 架构 / 合规 / 运营约束 |  |  |  |
| 本次决策 |  |  |  |
```

状态含义：

- `confirmed`：由权威项目材料或可验证产品行为确认；
- `user_stated`：用户明确陈述，但尚未由项目材料核验；
- `inferred`：基于现有材料推断；
- `unknown`：会影响分析但当前没有足够信息。

## 证据等级

按来源记录，而不是把所有证据压成一个“可信/不可信”标签：

1. 官方文档、定价、政策、发布记录；
2. 产品亲测或可复现行为；
3. 用户提供截图或录屏；
4. 可信第三方材料；
5. 用户陈述；
6. 分析推断。

高等级来源也只能证明其覆盖范围。例如官方营销页可以证明官方承诺，不能证明执行质量。

## 证据链表

```markdown
| 对象 | 来源 / URL / 文件 | 核验日期 | 获取方式 | 观察或推断 | 能证明什么 | 不能证明什么 | 置信度 |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

置信度建议使用 `high / medium / low`，并在存在冲突证据时保留冲突，不静默选择。

## 截图补证决策

只有以下情况通常需要截图：

- 登录后的核心流程决定本次判断；
- 公开文案与实际产品能力可能不一致；
- 需要判断任务状态、产物、审批、日志、恢复、计费或权限；
- 当前结论将直接影响高成本产品或架构决策。

必须补图时使用明确请求：

```markdown
这个页面无法公开访问，而它决定我们能否判断「[关键问题]」。请你必须补以下截图：
1. [页面]：完整覆盖 [信息]，用于判断 [结论]。
2. [页面]：完整覆盖 [信息]，用于判断 [结论]。

在拿到这些截图前，我只能确认 [现有证据]；关于 [关键能力] 的结论最高只能标为 speculative，不会进入 do_now。
```

如果截图只是有帮助而非必要，应先完成可交付版本，同时列出截图能升级哪些结论。

## 截图证据抽取

```markdown
| 竞品 | 页面 / 场景 | 可见模块 | 关键文案 / 价格 | 用户动作 | 可信机制 | 可证明 | 待验证 |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

重点抽取入口、主路径、状态、用户确认、失败提示、历史记录、价格/额度、外部副作用和恢复机制。
