# AI 产品竞品研究

目标不是复述竞品有什么，而是回答：这些证据会让当前项目改变什么、验证什么、坚持不做什么。

## 先建立研究决策框架

开始研究前，明确本次希望支持的 1-3 个决策，例如定位、MVP、功能优先级、Agent/Workflow、定价、支付/KYC、可信机制、架构、增长或留存。若用户没有明确提出，从上下文推断候选决策并标为 `inferred`，只在答案会实质改变时追问。

最少需要知道：

- 当前项目是什么、处于什么阶段；
- 已经构建或明确承诺了什么；
- 本次要分析的一个或多个竞品；
- 研究要支持什么近期决策。

若可以访问项目仓库、文档或工作区，先读取高信号材料，自行形成项目上下文卡，不要求用户重复填写。优先读取产品定位、当前版本边界、现有能力、架构原则、路线图、用户反馈和已确认决策。若无法访问项目，询问最低必要信息；用户要求直接研究时，可以基于明确假设继续。

项目上下文卡中的每项信息标注为 `confirmed`、`user_stated`、`inferred` 或 `unknown`。不要把愿景、规划和已上线能力混在一起。

需要完整的首次输入方式和上下文卡模板时，读取 [references/intake-and-evidence.md](references/intake-and-evidence.md)。

## 制定证据计划

优先使用当前可核验的一手来源：官网、产品页、定价页、官方文档、发布公告、可访问的产品后台和用户提供的截图。涉及当前价格、功能、政策或近期变化时必须重新核验。

为重要判断保留证据链：来源、访问日期、是否亲测、观察或推断、置信度、能证明什么、不能证明什么。截图只能证明界面、流程和产品承诺，不能单独证明后端真实执行、稳定性、支付闭环或商业结果。

链接不可访问、需要登录或关键后台不可见时，必须主动做出三选一判断：

1. `screenshot_not_needed`：公开资料足以支持当前决策，继续研究；
2. `screenshot_helpful`：截图会提升质量但不阻塞，先交付当前版本并列出建议补图；
3. `screenshot_required`：缺图会使核心判断不可靠，明确告诉用户必须补哪些页面、每张图要覆盖什么、为什么需要，以及缺图时结论的最高证据等级。

不要只说“方便的话请截图”。若用户决定不补图，继续研究并将相关结论降级为待验证。

## 识别真正的竞争关系

先分类，再比较：

- 直接竞品：目标用户、任务和购买理由高度相似；
- 间接竞品：解决同一目标中的部分环节；
- 用户替代方案：人工服务、通用工具组合、内部流程或不采取行动；
- 技术参考：提供底层模型、Agent 框架、支付、身份、基础设施或集成能力。

区分用户重叠、购买心智重叠和局部工具替代。检查竞品能力解决的是高频真实痛点、关键购买理由，还是主要用于演示和营销展示。

## 拆解产品能力

按研究问题选择维度，不机械填满矩阵。常用维度包括：定位与 ICP、首次使用、AI 角色、主动性与自治、任务/工作流、上下文与记忆、工具与连接器、人机确认、可信与恢复机制、交付物、协作、定价与额度、增长、合规与运营责任、反馈闭环。

对每项能力区分：可见产品表达、可验证执行深度、底层依赖、用户价值和商业价值。不要把 Agent 名称、标签或 UI 入口等同于真实能力。

## 按决策扩展趋势研究

只有当本次决策依赖市场时机、技术成熟度、用户行为变化、监管或生态变化时，才扩展趋势研究。可检查搜索与社区信号、产品发布与采用、技术/开源进展、投资与并购、标准和监管变化，并说明信号的时间范围与局限。

趋势信号用于解释竞品为什么现在出现、能力是否可能普及、进入窗口是否变化；它不能替代真实用户需求和交易验证。没有可靠数据时不硬算 TAM/SAM/SOM，不承诺预测准确率，也不以单一融资或热度事件证明趋势成立。

## 映射到当前项目

所有重要竞品结论都要经过项目约束过滤：

- 当前阶段与版本停止线；
- 核心用户、购买理由和产品身份；
- 已有能力、团队容量与交付时间；
- 商业模式、合规、支付和运营责任；
- 对核心对象、权限、状态、版本、审计、数据所有权和外部集成的影响。

对架构影响大的能力，明确它会改变 UI、Agent、Workflow、数据模型、Policy、权限还是外部服务。优先考虑人工或半自动验证路径，避免把长期平台能力直接升级为当前版本必做。

使用统一映射字段：竞品能力、证据、用户价值、项目现状、差距、阶段适配、复杂度、依赖、风险和建议。

需要评分规则、架构检查和需求候选字段时，读取 [references/scoring-and-decisions.md](references/scoring-and-decisions.md)。

## 收敛成决策

建议必须落入以下类别之一：

- `do_now`：证据充分、阶段适配、近期价值清楚；
- `test_first`：值得验证，但关键假设、需求或实现深度尚未证明；
- `do_later`：方向成立，但不符合当前阶段或依赖未满足；
- `do_not_do`：用户不匹配、稀释定位、复杂度/责任/合规风险过高，或已有更轻替代；
- `observe`：保留监测信号与触发条件，不进入当前路线。

重大建议在提交前做一次对抗式检查：给出支持该建议的最强证据，再给出不应跟进的最强反对意见，最后依据用户价值、证据强度、阶段成本、失败可恢复性和长期演进作出裁决。若反方成立，降级为验证项或观察项。

结论强度分为 `confirmed`、`likely`、`speculative`。`speculative` 不能直接进入 `do_now`。

最终交付至少包含：

- 一句话结论与本次研究支持的决策；
- 项目上下文及其置信状态；
- 竞品分类、关键证据和能力差异；
- 用户重叠、威胁、成熟度、商业压力与可借鉴度；
- `do_now / test_first / do_later / do_not_do / observe`；
- 对产品、架构、商业模式和验证计划的影响；
- 仍需用户决策、补充材料或真实业务验证的事项。

根据用户需要选择快速判断、完整报告或管理层决策摘要。需要可直接套用的结构时，读取 [references/report-templates.md](references/report-templates.md)。

## 边界

- 不把竞品存在的功能自动转成项目需求。
- 不用二手报道覆盖可获得的一手证据。
- 不为了报告完整硬凑市场规模、融资、预测精度或来源数量。
- 不替用户虚构已确认定位、预算、法律结论或商业结果。
- 研究产物默认是决策输入；除非用户明确要求，不直接修改项目路线图、PRD、架构或外部系统。
