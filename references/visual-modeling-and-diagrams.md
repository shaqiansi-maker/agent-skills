## 先判断图要回答什么

图表用于降低关系理解成本，不用于装饰或证明报告完整。

生成图之前先写出它要回答的一个问题，例如：

- 产品由哪些关键能力组成，它们如何协作；
- 用户任务从触发到交付经过哪些步骤；
- Agent、模型、工具和人工确认按什么顺序交互；
- 用户、空间、Agent、插件、凭据和数据对象是什么关系；
- 数据经过哪些边界，谁能读取、写入或批准；
- 正常、失败、重试、恢复和终止如何转换；
- 多个产品是直接竞品、替代方案还是技术参考；
- 哪些外部证据支持哪些结论和项目动作。

如果关系可以用一句话或一个两列表清楚表达，不生成图。深度报告必须判断是否需要图，但没有固定图数量。

## 图表选择器

| 需要解释的问题 | 首选表达 | 不应混入 |
| --- | --- | --- |
| 产品组成和能力依赖 | 能力架构图 / 分层图 | 未经证据支持的内部服务和技术栈 |
| 用户或业务任务如何完成 | 用户旅程 / 业务流程图 | 低层 API 调用细节 |
| Agent 如何理解、规划、执行和校验 | Agent 控制流图 | 把产品名称或角色名称当作权限 |
| 多主体调用、确认、超时和回调 | 时序图 | 静态对象归属 |
| 用户、空间、Agent、插件、凭据和业务对象关系 | 概念关系图；有实现证据时才用 ER 图 | 猜测的表、字段、主键和基数 |
| 数据移动、权限和安全边界 | 数据流图 / 信任边界图 | 仅凭隐私文案推断的真实部署拓扑 |
| 状态、事件、失败和恢复 | 状态图 | 没有定义事件或终态的流程箭头 |
| 产品间竞争、替代和参考关系 | 竞争关系图 | 把所有样本自动画成直接竞品 |
| 外部能力如何进入目标项目 | 项目能力映射图 / 决策 DAG | 未经项目基线支持的路线优先级 |
| 结论如何被证据支持 | 主张—证据—结论图 | 把来源类型等同于真实性 |
| 多产品在同一决策维度上的差异 | 对比表 / 决策矩阵 | 为了视觉效果生成没有刻度依据的雷达图 |

表格适合比较属性，图适合表达结构、方向、依赖、顺序和边界。两者可以配合，但不重复同一信息。

## 不同研究模式的默认候选

这些是候选组合，不是交付配额。只保留能改变理解或决策的图。

| 主模式 | 优先判断的图 |
| --- | --- |
| `product_deep_dive` | 能力架构图、核心任务流程图、概念关系或信任边界图 |
| `competitive_comparison` | 竞争关系图、共同能力分解图、决策矩阵 |
| `capability_benchmark` | 能力构成图、代表性实现时序图、控制与边界图 |
| `technical_adoption_review` | 系统上下文图、接入时序图、数据与权限边界图、失败恢复图 |
| `functional_validation` | 测试流程图、状态/恢复图、主张—证据—结果映射 |
| 带 `project_mapping` | 当前能力—外部能力—项目动作映射图，必要时增加采用决策 DAG |

同一报告可以跨模式，但不要因为覆盖层增加而机械叠加所有候选图。

## 事实、推断和未知如何进入图中

图中的确定性不能高于证据。每个关键节点或关系使用以下标签之一：

- `[已验证]`：由实测、接口、代码、后台记录或其他直接证据支持；
- `[已观察]`：界面或公开可见行为已观察，但底层机制未验证；
- `[厂商主张]`：仅由官方页面、销售材料或文档声明；
- `[推断]`：由多个事实支持但没有直接证据；
- `[未知]`：会影响结论但当前无法确认。

可以使用实线、虚线或颜色辅助区分，但不能只依赖颜色；文字标签必须保留。图旁记录关键 `Evidence ID`，不要把长引用塞进节点。

推断关系必须说明推断链和替代解释。没有证据不等于关系不存在。

## ER 图与概念关系模型的边界

区分三个层级：

1. **概念关系模型**：说明业务对象及其关系，例如用户属于空间、Agent 使用插件、调用产生审计记录。公开资料和界面观察通常最多支持这一层。
2. **逻辑数据模型**：说明实体、主要属性、基数、版本和生命周期。需要 API Schema、数据字典、代码、技术文档或稳定的跨界面证据。
3. **物理 ER 图**：说明表、字段、主外键、约束和存储实现。只有源码、数据库 Schema 或明确的实现文档才能支持。

证据只支持概念层时，标题必须使用“概念关系模型”或“推测性领域模型”，不得写成“数据库 ER 图”。不能从页面名、URL、JSON 示例或一个 API 返回值直接推断完整表结构。

## 主要图表的最低表达要求

### 能力架构图

至少标明用户价值层、核心能力层、执行或基础设施层，以及已知外部依赖。区分产品入口、真实能力和底层依赖。

### 流程图

至少标明触发、输入、主要步骤、决策分支、交付结果，以及与研究问题相关的失败、等待、取消或恢复路径。不要把中间生产步骤称为端到端流程。

### Agent 控制流图

至少区分系统自动触发、Agent 的理解/规划/执行/校验、确定性服务、人类输入或授权、外部副作用和失败出口。

### 时序图

至少标明主体、请求、凭据或上下文传递、返回、超时/错误，以及人工确认发生的位置。只画与结论相关的代表性序列。

### 概念关系图或 ER 图

至少标明对象名称、作用域、归属、关键关系和已知生命周期。基数、写入权、版本或状态未知时明确标记，不补猜。

### 数据流与信任边界图

至少标明数据来源、处理者、存储或临时驻留、权限检查、跨边界调用、审计点和外部去向。数据可被读取不等于可被发布、交付或跨项目复用。

### 状态图

至少标明状态、触发事件、合法转移、失败/超时、终态和恢复路径。产品未公开正式状态时使用“观察到的状态关系”，不伪造封闭枚举。

### 竞争关系图

至少区分直接竞品、工作流替代、能力提供者和设计参考，并写明分类依据。产品列表不自动等于竞品列表。

### 项目能力映射图

至少区分外部产品事实、可复用知识、项目现状、项目约束和建议动作。建议使用 `do_now / test_first / do_later / do_not_do / observe`，并标明项目依据。

### 主张—证据—结论图

至少保留 `Claim ID`、`Evidence ID`、证据状态、结论和行动。一个来源可以支持多个主张，但来源类型不能自动升级为真实性或归因。

## 图后说明模板

每张关键图后用简短文字说明：

```markdown
**图回答的问题：**
**作用域 / 版本：**
**证据基础：** Evidence E-01、E-04；其余虚线为推断
**置信度：** high / medium / low
**不表达：** 本图不代表数据库实现、生产部署或完整权限模型
```

不需要为显而易见的小图机械填满模板，但不得省略会导致误读的证据边界。

## 输出与降级规则

- Markdown 优先使用 Mermaid，便于维护和版本比较；环境不支持 Mermaid 时提供结构化表格或缩进关系清单。
- 一张图只回答一个主要问题。节点或交叉关系过多时按业务、Agent、数据或权限拆图。
- 图放在它支持的结论附近，不集中成与正文脱节的“图片画廊”。
- 先写准确模型，再考虑视觉美化。不得为了图形完整增加没有证据的对象、状态或连线。
- 图、表和正文冲突时，以证据等级最高的已核验事实为准，并修正其余表达。
- 同一关系只维护一份权威图；其他章节引用，不复制不同版本。
- 关键图在交付前检查 Mermaid 语法、方向、节点遗漏、移动端可读性和图文口径。
