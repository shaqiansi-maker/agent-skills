## 先给直接结论

所有交付先用简明语言回答：

1. 本次研究的对象和模式是什么；
2. 最重要的结论是什么；
3. 哪些已经验证，哪些只是主张或推断；
4. 结论对用户下一步意味着什么；
5. 仍然缺什么证据。

不要让读者必须读完整份报告才知道结论。

## 结构化决策摘要

深度报告先提供一页内可以扫描完的摘要。字段按任务裁剪，不为了模板完整填充无关内容：

```markdown
## 直接结论

| 项目 | 结论 |
| --- | --- |
| 研究模式 | product_deep_dive / competitive_comparison / capability_benchmark / technical_adoption_review / functional_validation |
| 核心判断 | 用一句到三句话直接回答决策问题 |
| 建议状态 | do_now / test_first / do_later / do_not_do / observe，或无项目条件下的适用结论 |
| 置信度 | high / medium / low，并说明主要原因 |
| 最强证据 | Evidence ID 与它实际证明的内容 |
| 关键未知项 | 当前不能确认且可能改变结论的事项 |
| 下一步 | 最轻可执行动作、成功标准和停止条件 |
```

评分不能代替结论。若不同子能力的证据强度不同，分别给出结论，不用一个综合分数掩盖差异。

## 可视化模型包

深度报告必须判断是否需要图，但不强制固定图数。选择能减少关系误读并改变理解或决策的最少图表：

| 报告类型 | 优先判断的图 |
| --- | --- |
| 单产品深度分析 | 能力架构图、核心任务流程图、概念关系或信任边界图 |
| 多产品竞品比较 | 竞争关系图、共同能力分解图、决策矩阵 |
| 能力专题研究 | 能力构成图、代表性实现时序图、控制与边界图 |
| 技术采用评估 | 系统上下文图、接入时序图、数据与权限边界图、失败恢复图 |
| 功能验证 | 测试流程图、状态/恢复图、主张—证据—结果映射 |
| 项目映射 | 当前能力—外部能力—项目动作映射图、必要时增加决策 DAG |

图放在对应分析附近，不单独堆成图片画廊。每张关键图说明它回答的问题、作用域/版本、证据基础、置信度和不表达什么。

图中的节点和关系区分 `[已验证]`、`[已观察]`、`[厂商主张]`、`[推断]` 和 `[未知]`。只依赖官网、页面或公开接口时，不得把概念关系模型写成数据库 ER 图，也不得补猜表、字段、主键或基数。

具体选择规则、最低表达要求和 Mermaid 降级方式见 [visual-modeling-and-diagrams.md](visual-modeling-and-diagrams.md)。

## 截图证据如何进入报告

截图用于展示关键可见证据，不用于装饰。只有截图能显著增强重要结论，且文字或表格不足以准确表达时，才将去敏后的最小必要画面放在结论附近；其他截图只保留 Evidence ID。

说明保持简短：Evidence ID、来源与核验时间、证明什么、不能证明什么。环境、版本、角色等只在影响判断时补充。自动化测试优先保留决定性检查点、失败现场和关键前后状态，不形成过程截图墙。

## 正文裁剪规则

正文服务于理解和决策，不服务于模板完整。一个章节、表格、截图或图如果不改变核心结论、证据边界、风险、适用条件或下一步行动，应删除、合并或移入附录。

先给直接结论，再保留支撑决策的必要分析；完整测试过程、重复运行、原始截图和日志仅在需要时进入附录。删除礼仪性开场、研究过程叙事、重复总结、无决策意义的背景和为了填满模板生成的章节。需要表达不确定性时，准确写明“什么未知、为什么未知、会影响哪个结论、如何验证”，不用未限定的模糊形容词替代判断。

## 快速研究

适合单个问题、公开资料判断或早期筛选：

```markdown
# [主题] 快速判断

## 直接结论
## 研究对象与范围
## 已验证事实
## 关键能力或差异
## 对用户意味着什么
## 证据边界与下一步
```

不强制生成独立证据文件，但重要事实要有就近来源。

## 单产品深度分析

```markdown
# [产品] 深度分析报告

## 1. 直接结论和阅读指引
## 2. 研究问题、范围与证据深度
## 3. 产品定位、用户和购买理由
## 4. 核心任务与价值闭环
## 5. 能力、Agent 和工作流构成（按需附能力架构图、流程图或控制流图）
## 6. 数据、对象关系、权限、审计和安全边界（按需附概念关系图或信任边界图）
## 7. 用户体验、失败与恢复
## 8. 商业、交付与成熟度
## 9. 功能验证结果
## 10. 未来演进：事实、推断与触发条件
## 11. 可复用设计原则与反模式
## 12. 项目映射或无项目适用条件
## 13. 对抗式审视
## 14. 未验证事项和下一步
```

## 多产品竞品比较

```markdown
# [主题] 竞品分析报告

## 1. 直接结论
## 2. 决策问题、项目基线与停止线
## 3. 竞品、替代方案和技术参考分类（按需附竞争关系图）
## 4. 用户、任务、预算和购买理由重叠
## 5. 决策相关能力对比（按需附共同能力分解图和决策矩阵）
## 6. 单个竞品关键拆解
## 7. 威胁、机会与成熟度
## 8. 项目映射与决策
## 9. 对抗式审视
## 10. 证据和待验证事项
```

只比较能改变本次决策的维度，不生成无意义的大而全矩阵。

```markdown
# [产品 / 能力] 采用与验证报告

## 4. 正常、异常、权限和恢复测试

## 8. 风险、控制和下一步
## 9. 清理结果与遗留项
```

## 深度任务的证据包

根据实际需要生成，不强制每次全部落盘：

```text
report.md
evidence/
  claim-ledger.md
  evidence-index.md
tests/
  test-matrix.md
models/
  model-index.md
artifacts/
  index.md
decisions.md
```

原始截图、Trace、日志和导出文件保存在受控位置，不默认全部复制进公开报告；符合“截图证据如何进入报告”条件的去敏关键截图应放在对应结论附近。`artifacts/index.md` 记录位置、敏感性、保留期限、正文引用和是否已清理。图直接维护在报告中即可；只有图较多、需要单独复用或需要保留源文件时才建立 `models/`，并在 `model-index.md` 记录图回答的问题、证据状态和引用位置。

## 写作与证据要求

- 用通俗语言给结论，不牺牲准确边界；
- 正文按决策价值裁剪，不保留礼仪性开场、重复总结和无作用模板章节；
- 引用尽量放在对应判断附近；
- 事实、厂商主张、观察、推断和建议分开；
- 未来演进必须标明是公开规划、基于证据的推演还是纯候选；
- 表格过宽时按产品、架构、商业或证据主题拆分；
- 图表用于结构、方向、顺序、依赖和边界，不与表格重复同一信息；
- 图中的对象、连线、状态、基数和部署关系不得超过证据强度；
- 关键截图就近支持具体主张，并注明来源、时间、环境和不能证明的内容；
- 截图、图表、表格和文字不重复表达同一信息；
- Mermaid 不可用时提供结构化表格或缩进关系清单，不省略关键关系；
- 没有证据的内容写未知，不用确定语气填补；
- 不确定性使用具体未知项、原因、影响和验证方式表达，不使用未限定的模糊形容词；
- 最终说明测试材料和敏感信息是否清理。
