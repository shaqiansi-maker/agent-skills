## 适用范围

当待验证主张涉及生成质量、检索、记忆、规划、工具选择、Agent 执行、工作流协作或其他具有概率性、上下文依赖的 AI 行为时使用本方法。

普通页面入口、确定性字段、固定 API Schema 或单纯连通性可以按常规功能测试处理，不必为了形式引入 AI 评测。

## 参与方式

默认使用 `agent_led`，只有用户不可替代时才新增交互：

| 模式 | 谁执行 | 用户何时介入 |
| --- | --- | --- |
| `agent_led` | Agent 建立并执行测试、记录证据、复核和清理 | 授权、凭据、不可替代事实或高风险决定 |
| `collaborative` | Agent 设计与复核，用户完成受限步骤或同步体验 | 登录、验证码、封闭页面、主观体验或现场操作 |
| `user_led` | 用户按测试方案操作，Agent 提供观察点并校验结果 | 用户明确要求亲自验证，或 Agent 无法接触环境 |

用户已有明确授权且测试完全落在授权范围内时，不重复要求逐步确认。范围、成本、数据或外部副作用扩大时必须停止并重新获得授权。

## 从主张建立评测契约

先定义要证明什么，不先收集一堆看似完整的案例：

```markdown
### AI 评测契约
- 待验证主张：
- 能力对象与边界：
- 产品 / 模型 / Prompt / 工具 / 知识 / 配置版本：
- 环境、账户、地区与权限：
- 代表性用户任务：
- 明确非目标：
- 预期行为与不可接受行为：
- 任务集与重复策略：
- 基线或对照：
- 评判方式与通过条件：
- 允许动作与禁止动作：
- 停止条件与清理方式：
```

产品没有公开内部模型、Prompt 或配置时写 `unknown`，不要反推虚构。测试目标是验证可观察行为，不是猜测内部实现。

## Agent 自主执行流程

取得授权后，Agent 默认自行完成：

1. 检查当前宿主能否访问产品、项目、浏览器、API/MCP、文件、日志和必要测试工具；
2. 选择隔离环境、Demo、测试空间、测试账号或去敏数据，不默认使用生产环境；
3. 建立最小但有区分度的任务集、输入夹具、基线和通过条件；
4. 先运行低风险冒烟用例，确认凭据、范围和证据记录正常；
5. 执行代表性任务、边界任务、失败任务和必要的重复运行；
6. 保存实际输入、配置、输出、工具 Trace、调用编号、时间、成本和异常；
7. 使用与主张匹配的确定性校验、语义评判或人工复核，不让生成结果自行宣布通过；
8. 发现新权限、写操作、显著费用或不可逆副作用时停止并请求授权；
9. 按约定清理测试数据、临时服务、凭据和配置，并记录无法清理的遗留项。

无法自动完成的步骤只转交给用户必要部分，不把整套验证退回用户。

## 任务集与重复运行

任务集应覆盖会改变结论的差异，而不是追求数量：

- 典型正常任务；
- 语义相同但表达不同的任务；
- 信息不足、含糊或互相冲突的任务；
- 工具失败、依赖超时和空结果；
- 越界要求、危险动作和不应执行的任务；
- 用户修改、撤回、恢复和连续上下文任务；
- 对产品主张最不利但合理的反例。

重复策略由主张决定：

- 确定性连接和 Schema 主张主要验证输入、输出、错误和重复调用一致性；
- 生成质量、规划和工具选择需要多个代表性任务，并对关键任务重复运行以观察波动；
- 记忆和长流程需要跨轮次、跨阶段或重新进入后的连续性测试；
- 高风险结论需要独立校验、第二评判路径或人工复核；
- 样本不足时只报告观察结果，不输出稳定性、成功率或普遍性结论。

不机械规定固定运行次数。记录选择当前样本和次数的理由，以及它不能覆盖的范围。

## 评判方式

按结果性质选择评判者：

| 结果 | 优先评判方式 |
| --- | --- |
| Schema、状态、权限、数值、文件和外部事实 | 确定性断言或目标系统核对 |
| 检索引用、事实依据 | 来源匹配、引用覆盖和事实核查 |
| 表达质量、相关性、完整性 | 明确 Rubric 的语义评判，必要时人工复核 |
| 工具选择与参数 | Trace、参数和目标系统结果核对 |
| 业务是否有用 | 由具备业务背景的人判断，不由模型代替 |
| 安全和越权 | Policy、拒绝行为、服务端结果和审计证据 |

记录评判者、Rubric、模型或脚本版本。能用确定性校验解决的问题，不只使用 LLM 评分；使用模型评分时，避免让同一个生成过程只凭自身解释判定通过。

## 常用观察维度

只选择与主张有关的维度：

- 任务是否真正完成，而非只生成了说明；
- 事实是否准确，引用是否支持结论；
- 工具是否选对，参数、顺序和作用域是否正确；
- 是否遵守权限、授权、预算和禁止动作；
- 面对缺失、冲突和未知信息时是否会澄清或降级；
- 失败后是否可重试、恢复、撤回或人工接管；
- 跨轮记忆和状态是否正确，不混入其他用户或项目；
- 多次运行是否出现影响决策的波动；
- 延迟、用量和成本是否符合实际使用条件；
- 输出是否可解释、可追溯并能被后续流程使用。

不要把不同对象压成一个统一总分。硬性权限、安全和事实错误不能被平均分抵消。

## 安全与对抗性用例

只在明确授权的隔离环境内检查：

- 输入内容是否能诱导 Agent 忽略系统规则或调用无关工具；
- 工具返回、网页或文件中的指令是否被错误当成授权；
- 是否读取、记忆或输出超出当前用户、项目和任务的数据；
- 写入、发布、支付、删除等动作是否在执行前重新校验授权；
- 日志、Trace 和错误信息是否泄露凭据或敏感数据。

这不是渗透测试授权。不得扫描、攻击或尝试访问未获授权的账户和生产数据。

## 结论和清理

结论必须同时写明：

- 哪个版本、账户、环境和任务集下观察到什么；
- 样本和重复运行范围；
- 使用了什么评判方式；
- 哪些结果稳定、波动或相互冲突；
- 能证明和不能证明什么；
- 测试资产、凭据和数据是否已清理。

单次成功只能作为一个观察事实。只有任务集、重复运行和评判方式与主张匹配时，才可以形成更强的能力结论。
