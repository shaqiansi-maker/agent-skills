## 目标

用最低沟通成本识别用户真正想研究的对象、范围和决策，不把产品清单自动解释成完整竞品分析。

## 先识别三个要素

### 1. 研究单位

- `product`：一个产品本身；
- `competition`：多个产品之间的竞争关系；
- `capability`：一个或多个跨产品能力；
- `adoption`：某产品或能力能否采购、接入或使用；
- `claim`：某项宣传或功能是否真实成立。

### 2. 用户要作出的决定

- 理解产品；
- 比较竞争与替代；
- 提炼能力和设计方法；
- 为项目选择优先级；
- 选型、采购或接入；
- 验证功能、安全或商业主张。

### 3. 证据深度

- 公开资料即可；
- 需要登录观察；
- 需要隔离实测；
- 需要 API/MCP/代码检查；
- 需要报价、合同、客户或运营证据。

## 自动路由

| 请求特征 | 主模式 | 默认边界 |
| --- | --- | --- |
| 一个产品 + “分析、看看、怎么运作” | `product_deep_dive` | 完整理解该产品，不自动映射项目 |
| 多个产品 + “对比、竞品、谁更适合” | `competitive_comparison` | 比较竞争关系与决策相关差异 |
| 多个产品 + “共同、某项能力、都怎么做” | `capability_benchmark` | 能力是主体，产品是样本 |
| “适不适合、能否接入、怎么买、怎么部署” | `technical_adoption_review` | 重点检查采用条件、成本和风险 |
| “是不是真的、能不能跑通、帮我测试” | `functional_validation` | 建立可复现测试，不扩张成完整审计 |
| “结合当前项目、我们要不要做” | 增加 `project_mapping` | 先确认目标项目并读取基线 |
| “Schema、权限、审计、数据、安全边界” | 增加 `architecture_review` | 检查对象、权威、作用域和失败路径 |

模式可以组合，但只选择一个主模式。例如：

- “深度分析 Carrier，并测试 MCP” = `product_deep_dive + functional_validation`；
- “比较 A/B/C 的记忆能力并用于当前项目” = `capability_benchmark + project_mapping`；
- “评估某 API 是否值得采购” = `technical_adoption_review + commercial_review`。

## 最小沟通规则

### 请求明确

不追问。用一句话复述并继续：

```text
我理解为：以 MCP、权限和审计为研究对象，A/B/C 是样本；重点提炼共同模式、差异和项目启发，不做完整竞品画像。我按这个范围继续。
```

### 可以合理推断

说明假设后继续，不等待形式确认：

```text
你没有指定目标项目，我先按无项目的能力专题研究处理，输出可复用模型和适用条件；不会给出具体路线优先级。
```

### 存在实质歧义

只问一个会改变结论的问题：

```text
这次主要想比较完整产品，还是只研究其中某项能力，例如 Agent、工作流、MCP、权限或商业化？
```

以下情况通常需要追问：

- 产品清单存在，但没有研究对象或目标；
- “适合我们”但目标项目不明确；
- 公开研究与登录实测会导致明显不同的工作量或授权；
- 输出用于高成本采购、架构建设或外部发布，但决策标准未知。

不要为了完善表格追问低影响信息。用户不回答时，采用最保守、可逆的解释并标明假设。

## 研究任务卡

任务卡供 Agent 内部使用，不要求用户填写：

```markdown
### 研究任务卡
- 主模式：
- 覆盖层：
- 研究单位：产品 / 竞争 / 能力 / 采用 / 主张
- 产品或样本：
- 重点能力：
- 用户要作出的决定：
- 目标项目状态：target_project_confirmed / project_context_unconfirmed / no_target_project
- 证据深度：
- 实测参与方式：agent_led / collaborative / user_led / not_applicable
- 明确不做：
- 输出形式：对话 / 报告 / 证据包
- 停止线：
```

## 范围防误读

- 产品数量不决定研究模式；
- 产品样本不自动等于直接竞品；
- 用户只点名局部能力时，不扩张到全部功能；
- 用户提供大量截图时，只处理与研究主张相关的部分；
- “全面一些”表示覆盖当前决策需要的维度，不表示收集所有公开资料；
- “深度分析”表示追溯运行机制、边界和证据，不表示默认进行安全攻击或生产测试。

## 路由验收样例

| 输入 | 预期路由 |
| --- | --- |
| “分析 Carrier” | `product_deep_dive` |
| “Carrier 和 Dify 谁更适合企业内部 AI” | `competitive_comparison + technical_adoption_review` |
| “研究 Carrier、Dify、扣子的 MCP 权限设计” | `capability_benchmark + architecture_review` |
| “这个 Connector 能否接到我们的项目” | `technical_adoption_review + project_mapping` |
| “官网说支持审计，帮我证明一下” | `functional_validation + architecture_review` |
| “看看这些产品说明了什么” | 追问完整产品趋势还是指定能力模式 |
