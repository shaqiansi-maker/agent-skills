# AI 产品研究

目标不是罗列功能，而是形成**有证据边界、可被理解并能推动下一步行动**的结论。

目标项目是可选输入，但可使用的研究成果是强制输出：有项目时形成项目决策；无项目时形成可复用的能力模型、设计原则、测试方法和适用条件。

## 适配运行环境

这是平台无关的 Agent Skill。使用当前 Agent 实际具备的项目读取、网页访问、图像理解、浏览器操作、API/MCP 调用和文件写入能力，不假设特定平台、工具名或安装路径。

能力不足时降级而不是虚构：

- 无法读取项目：索取会改变结论的最低必要信息，或按无项目模式研究；
- 无法访问网页：使用用户提供的文档、截图和摘录，降低相关结论等级；
- 无法理解附件：请用户提供关键文字、页面结构或录屏说明；
- 无法实测：明确哪些只能确认官方主张，不能确认实际执行；
- 无法写文件：在对话中交付，并说明尚未形成落盘成果。

安装或调用本 Skill 不代表用户授权注册、购买、修改项目、访问敏感数据、写入外部系统或测试生产环境。任何外部副作用、凭据使用、写操作或高成本测试都要在执行前单独获得授权。

## 1. 先识别用户真正要研究什么

不要根据产品数量机械选择报告类型。先判断**研究单位**和**决策目标**。

选择一个主模式：

- `product_deep_dive`：理解一个产品的定位、能力、运行机制、边界和成熟度；
- `competitive_comparison`：比较多个产品对同一用户、任务、预算或购买理由的竞争关系；
- `capability_benchmark`：把某一种或几种能力作为研究主体，产品只是证据样本；
- `technical_adoption_review`：评估产品、平台、API、MCP 或基础设施能否安全、经济地接入；
- `functional_validation`：验证产品宣传或关键功能是否在指定环境中实际成立。

可以增加以下覆盖层，但不要让覆盖层替代主模式：

- `project_mapping`：映射到指定项目；
- `commercial_review`：分析定价、交付、采购与商业成熟度；
- `architecture_review`：分析对象、数据、权限、审计、执行和恢复边界。

明确请求不重复提问。信息足够时，用一句话复述研究对象、范围和不做内容后直接继续。只有两种解释会显著改变结论、成本或证据要求时，才问一个高价值问题。

多个产品加某项能力时，默认进入 `capability_benchmark`，而不是完整竞品矩阵。产品列表不自动等于竞品列表。

完整路由规则和最小沟通方式见 [references/intent-routing-and-intake.md](references/intent-routing-and-intake.md)。

## 2. 建立研究契约和停止线

内部建立一张研究任务卡，至少明确：

- 主模式、研究单位和产品样本；
- 要支持的近期决策或知识目标；
- 重点能力与明确不做范围；
- 目标项目是否存在、是否已确认；
- 所需证据深度；
- 时间、访问、授权和输出限制；
- 什么时候信息已经足够，停止继续扩张。

不要要求用户填写长问卷。能从用户请求、当前会话或已确认项目材料中得到的信息不再询问。

## 3. 判断项目上下文

项目有三种状态：

- `target_project_confirmed`：用户明确指定项目，或明确说“当前项目 / 我们的项目”；
- `project_context_unconfirmed`：工作区里存在项目，但用户没有说明它是本次目标；
- `no_target_project`：本次不依赖具体项目。

不要因为当前打开了某个仓库就自动把它当成目标项目。项目未确认且映射会改变结论时，只问一次；用户只要通用研究时，不强迫提供项目。

有目标项目时，优先读取定位、愿景、目标用户、当前阶段、版本边界、已构建能力、已承诺能力、架构原则、商业与运营约束以及已确认决策。每项标记 `confirmed / user_stated / inferred / unknown`。

无目标项目时，输出条件式结论、适用边界和未来采用条件，不虚构路线优先级。

项目读取与决策转译见 [references/project-context-and-decision-transfer.md](references/project-context-and-decision-transfer.md)。

## 4. 先建主张，再找证据

不要先漫无目的搜索。先列出会影响结论的关键主张，例如：

- 产品服务谁、解决什么任务；
- 某能力是否存在、执行到什么深度；
- 权限、数据、审计和恢复边界是否成立；
- 定价、部署和商业承诺是否有公开依据；
- 某模式是否适合目标项目。

对每个关键主张记录：决策影响、需要什么证据、准备通过什么路径验证，以及拿不到证据时结论最多能到什么强度。

证据围绕主张组织，不把官网、截图、实测和第三方材料简单压成同一个可信等级。官方页面能证明官方主张，界面能证明可见交互，成功调用能证明特定环境下的执行，审计记录能证明可追溯性，第三方材料才能补充市场采用或客户结果。它们不能互相替代。

主张、证据对象、状态和冲突处理见 [references/claim-and-evidence-model.md](references/claim-and-evidence-model.md)。

## 5. 选择最低充分的证据路径

按决策风险选择证据深度：

1. `public_research`：官网、文档、定价、政策、发布记录和可信第三方材料；
2. `authenticated_observation`：登录后台观察核心流程、状态、权限和结果；
3. `isolated_functional_test`：在隔离环境中执行可复现功能测试；
4. `protocol_or_source_review`：检查 API、MCP、Schema、调用结果、代码或实现文档；
5. `commercial_validation`：通过合同、报价、客户案例、采购材料或访谈核验商业主张。

链接不可访问、需要登录或关键页面不可见时，明确判断：

- `evidence_not_needed`：现有证据足以支持当前决策；
- `evidence_helpful`：补充材料可提高置信度，但不阻塞交付；
- `evidence_required`：缺失将使关键结论不可靠，明确要求用户必须提供什么、用于证明什么。

不要笼统地说“方便的话发截图”。若用户不补充，继续完成可完成部分，并降低相应结论强度。

## 6. 需要实测时采用可复现测试

只有测试结果会改变重要结论时才实测。测试前明确环境、账户、版本、权限、数据范围、允许动作、停止条件和清理方式。

代表性测试至少覆盖与本次主张相关的：

- 正常路径；
- 非法或缺失输入；
- 权限与作用域；
- 失败、超时或服务不可用；
- 重试、恢复与历史记录；
- 外部副作用和测试清理。

每个测试记录前置条件、输入、预期结果、实际结果、截图/Trace/调用编号等证据，以及它能证明和不能证明什么。

测试通过只证明“该版本、账户、环境和任务下观察到成功”，不自动证明完整产品、生产稳定性或所有客户场景成立。

UI、API、MCP、Agent、权限和清理方法见 [references/hands-on-testing.md](references/hands-on-testing.md)。

## 7. 分析产品，不把入口当能力

先识别产品类型：AI 应用、Agent/工作流平台、模型或 API 服务、MCP/连接器、开发者工具、企业 AI 基础设施，或它们的组合。不同类型使用不同分析重点。

根据研究目标选择维度，不要求每次填满全部矩阵。常用维度包括：定位与 ICP、核心任务、价值闭环、AI 角色、主动性、工作流、上下文与记忆、工具与连接器、数据与权限、人机确认、错误与恢复、输出与交付、协作、商业模式、部署、运营责任和成熟度。

对每项能力区分：官方表达、可见交互、实际执行、底层依赖、用户价值、商业价值和证据边界。Agent 名称、标签、入口或演示不等于真实能力。

详细框架见 [references/product-analysis-framework.md](references/product-analysis-framework.md)。

## 8. 将结果转成可使用的成果

始终分开三层结论：

1. **产品事实**：观察到什么，证据是什么；
2. **可复用知识**：由多个事实支持的能力模型、设计原则、测试方法和适用条件；
3. **项目决策**：结合目标项目的定位、阶段、现状和约束后采取什么行动。

有目标项目时，把建议归入：

- `do_now`
- `test_first`
- `do_later`
- `do_not_do`
- `observe`

无目标项目时，改为条件式建议：适合什么场景、需要什么前提、主要代价是什么、什么情况下不应采用，以及未来如何验证。不得声称它应进入某个不存在的路线图。

评分、对抗式审视和决策转译见 [references/scoring-and-decisions.md](references/scoring-and-decisions.md)。

## 9. 先给直接结论，再给完整证据

交付先回答：

- 研究对象是什么；
- 最重要的结论是什么；
- 已验证到什么程度；
- 对用户下一步意味着什么；
- 还不能确认什么。

再按需要提供完整报告、主张台账、证据索引、测试矩阵和项目决策表。快速研究不强制生成多份文件；深度分析或功能验证应让关键结论可追溯到证据。

交付结构见 [references/report-and-evidence-pack.md](references/report-and-evidence-pack.md)。

## 完成闸门

只有满足至少一项才算完成：

- 推进了一个具体项目决策；
- 形成了可执行的选型、采购、接入或验证方案；
- 沉淀了可跨项目复用的能力模型和测试方法；
- 有证据地说明某方向当前不值得采用；
- 把未知问题转成了可执行的验证任务和停止条件。

完成前检查：

- 产品列表是否被误当成竞品列表；
- 用户只研究局部能力时，是否错误扩成完整报告；
- 产品事实、分析推断和项目建议是否分开；
- 关键主张是否能回到证据；
- “没有证据”是否被错误写成“不存在”；
- 官网主张、截图、成功调用、后台审计和商业结果是否被混用；
- Demo 是否被错误推广为生产能力；
- 无目标项目时是否虚构了路线优先级；
- 测试环境、凭据、临时服务和敏感材料是否按约定清理；
- 置信度最低的判断是否被写得过于确定。

## 边界

- 不把竞品功能自动转成项目需求；
- 不把多个品牌自动定义为直接竞品；
- 不用二手材料覆盖可获得的一手证据；
- 不为了报告完整硬凑市场规模、融资、来源数量或评分；
- 不替用户虚构定位、预算、法律结论、客户结果或生产能力；
- 不执行未授权的生产测试、安全攻击、购买、注册、写入或外部发布；
- 研究成果默认是决策输入，除非用户明确授权，不直接修改项目路线图、PRD、架构或外部系统。
